== v2.3.24.68 — 2026-06-02

=== Corrigé

* **Admonition (NOTE/TIP/…) : 1re ligne décalée à droite & non
  justifiée.** Quand `crystal-asciidoctor` rend le corps d'une
  admonition, il enveloppe l'HTML inline dans
  `<div class="paragraph">\n<p>…</p>\n</div>`. Le `\n` entre
  `<div>` et `<p>` était conservé par `InlineRenderer.parse_html`
  comme un segment initial blanc-seulement, qui se propageait
  ensuite dans `wrap_segments` comme un espace de tête —
  décalant visuellement le premier mot (ex. `beryl`) d'environ
  une largeur d'espace par rapport aux lignes suivantes.
  `parse_html` ignore désormais un buffer blanc-seulement
  **uniquement quand c'est le tout premier segment** (sans
  impact sur les espaces inter-mots plus loin dans le flux).

* **Corps d'admonition non justifié.** `convert_admonition`
  appelait `render_segment_line` sans `target_w` / `align`,
  donc le pipeline de justification (`max_extra_factor`,
  distribution par espace) ne se déclenchait jamais. Il passe
  désormais `content_w` et `@theme.base_text_align`, avec la
  dernière ligne forcée à `"left"` (cohérent avec
  `render_inline_lines`).

* **Garde-fou de justification trop strict sur les contenus
  étroits.** `max_extra_factor` relevé de `1.5` à `2.5` × la
  largeur normale d'espace. Le plafond à 1.5 bloquait des
  justifications légitimes sur des lignes peu espacées ou avec
  mots longs (ex. `un serveur bare-metal…`,
  candidat 5,16 pt > limite 4,77 pt). Le plafond à 2.5 attrape
  toujours les vrais cas pathologiques (mot isolé seul, mise en
  page cassée) sans rejeter de vrais paragraphes.

== v2.3.24.65 — 2026-06-02

=== Ajouté

* **Rendu du code inline (codespan).** Nouvelle catégorie de
  thème `codespan_*` portée de la spec `asciidoctor-pdf` Ruby
  2.3.24 : fond grisé + bordure optionnelle + couleur de texte +
  padding configurable derrière les segments inline en `` `text` ``.
  Avant ce port, le code inline était rendu en police mono mais
  sans aucun habillage visuel — `_default.yml` ressemblait à du
  texte ordinaire.

* **Typographie française (extension `x-`).** Nouvelle propriété
  de thème `x_french_typography` (`true` par défaut dans le thème
  `fr`, `false` ailleurs). Quand active, le converter remplace
  l'espace ordinaire devant `:`, `;`, `!`, `?`, `»` et après `«`
  par un espace insécable U+00A0 — respecte la règle de
  l'Imprimerie nationale et évite les retours à la ligne
  inappropriés au milieu d'une ponctuation à deux parties.
+
Les blocs de code (`[source,...]`, ` ```), les blocs literal et
les attributs (style, language) sont **préservés** car ils ne
passent pas par le pipeline inline parser.

* **Markup inline préservé dans les items de liste.** Auparavant
  `render_list` passait le texte de chaque item par
  `strip_inline_markup` + `draw_text_run` brut — résultat : tous
  les italiques, gras, code inline, liens, etc. étaient *strippés*
  et rendus comme du texte plat. Désormais le pipeline complet
  (`InlineRenderer.parse` + `wrap_segments` + `render_segment_line`)
  est utilisé, identique à celui des paragraphes. Le justify
  s'applique aussi aux items longs (lignes non-terminales).
+
Propriétés exposées dans le thème (defaults conformes au défaut
asciidoctor-pdf upstream) :
+
[cols="2,2,3"]
|===
| Propriété | Défaut | Effet

| `codespan_background_color`
| `f5f5f5`
| Fond gris très clair derrière le code

| `codespan_border_color`
| _vide_
| Bordure désactivée par défaut

| `codespan_border_width`
| `0.0`
| Idem

| `codespan_font_color`
| _vide_
| Hérite de la couleur de texte courante

| `codespan_padding_x`, `codespan_padding_y`
| `2.0`, `1.0`
| Espace autour du texte (points)
|===

* **Paragraphes justifiés par défaut** (`base_text_align: "justify"`).
  Le rendu distribue l'espace inutilisé d'une ligne entre les
  espaces inter-mots ; la dernière ligne d'un paragraphe reste
  alignée à gauche pour ne pas étirer un orphelin. Configurable
  via la propriété `base_text_align` du thème (valeurs : `"left"`,
  `"center"`, `"right"`, `"justify"`). Conforme à
  l'asciidoctor-pdf Ruby où `base_align: justify` est le défaut.
+
Algorithme : pour chaque ligne sauf la dernière, on calcule la
largeur naturelle des segments, on compte les espaces internes,
puis on répartit `(cible − naturelle) / n_espaces` après chaque
segment proportionnellement au nombre d'espaces qu'il contient.
Approximation simple (les espaces *entre* segments sont étirés,
ceux internes à un seul segment restent fixes) — suffisante pour
les paragraphes ordinaires avec markup léger (italique, code
inline, etc.).

=== Modifié

* Dépendance `crystal-asciidoctor` bumpée à **`~> 2.0.26.6`** —
  les blocs hybrides `[source,LANG]` + `\`\`\`` (forme acceptée par
  Asciidoctor Ruby en mode de compatibilité Markdown) reçoivent
  désormais correctement leur attribut `language`. Conséquence :
  coloration syntaxique + fond grisé + classe `language-LANG`
  appliqués comme pour la forme canonique `[source,LANG] ----`.

== v2.3.24.64 — 2026-06-02

=== Modifié

* **Les fontes CJK se rendent désormais nativement.** Contrainte
  `pdf` passée à `~> 0.6.4`, qui ajoute le subsetting et l'embedding
  natifs des fontes OpenType/CFF (`.otf`). Toutes les Noto CJK sont
  distribuées en `.otf` ; jusqu'ici elles déclenchaient
  `UnsupportedFontFormat` et les caractères CJK retombaient sur `?`.
  Avec pdf 0.6.4, une fonte Noto CJK en cache est chargée
  paresseusement au premier caractère CJK et embarquée en subset
  `CIDFontType0` — les idéogrammes se rendent et le texte est
  extractible.
* Commentaires de l'accesseur paresseux `font_cjk` mis à jour : le
  `rescue UnsupportedFontFormat` est désormais un filet de sécurité
  pour une fonte réellement corrompue / exotique, plus le chemin
  attendu du CJK.

=== Corrigé

* La spec d'intégration `non_winansi_chars_spec` ne code plus en dur
  l'attente obsolète « CJK → `?` ». Elle teste désormais le
  comportement selon la présence d'une fonte Noto CJK en cache
  (rendue, pas de `?`) ou son absence (fallback `?`). La limite
  Identity-H du helper d'extraction de texte est documentée (il lit
  les GID bruts, pas le ToUnicode, donc il ne peut pas reproduire le
  texte CJK exact — seulement la présence / absence du `?`).

== v2.3.24.63 — 2026-06-02

=== Corrigé

* **Blocs attachés aux items de liste rendus correctement.** Quand
  un item de liste numérotée (ou à puces) avait un bloc attaché
  via `+` (typiquement un bloc source `[source,console] ----`,
  une admonition, un tableau, un autre paragraphe), `render_list`
  itérait uniquement sur les *sous-listes* et ignorait
  silencieusement tous les autres types de blocs enfants.
+
Conséquence : dans les recettes de type « 1. Étape avec sa
commande / 2. Étape suivante avec sa commande » (très fréquent
dans les READMEs aloli-crystal), seuls les libellés des étapes
apparaissaient dans le PDF, les commandes disparaissaient.
+
Fix : tous les blocs enfants des items sont désormais routés via
le dispatcher général (`dispatch(sub_block, sub_block.context.to_s)`)
qui appelle le bon `convert_*` selon le type.

== v2.3.24.60 — 2026-06-01

=== Corrigé

* **Chargement de la police CJK véritablement paresseux.** En
  v2.3.24.59, l'accesseur `font_cjk` était paresseux, mais
  `text_with_emoji_segments` l'appelait **dès le premier run de
  texte** du document — ce qui déclenchait l'avertissement
  `UnsupportedFontFormat` (.otf CFF non supporté) pour *tout*
  document, y compris ceux n'ayant aucun caractère CJK.
* Désormais, `font_cjk` n'est sollicitée que pour un caractère
  *plausiblement CJK* (`ord >= 0x3000` — début de l'espace
  CJK Symbols and Punctuation). En-dessous, on est sur du Latin
  ou de la ponctuation typographique européenne (apostrophe
  courbe `'`, tiret cadratin `—`, points de suspension `…`, etc.)
  que la fonte CJK ne couvre pas — inutile de la charger pour
  s'en rendre compte. Conséquence : les documents européens
  sans CJK ne déclenchent plus l'avertissement.
* L'avertissement reste émis **une seule fois** quand un vrai
  caractère CJK (japonais, chinois, coréen, etc.) est rencontré
  dans le document.

== v2.3.24.14 — 2026-04-26

**Rendu des glyphes CJK** via le nouveau shard
https://github.com/aloli-crystal/noto-cjk[noto-cjk].

`noto-cjk pull` ou `CrystalNotoCJK::Cache.pull`), le

  de police mid-run est fait inline dans `draw_text_run`.
* `load_theme_fonts` charge opportunistement
  `CrystalNotoCJK.font_path` si une variante est en cache.
  Aucun téléchargement n'est déclenché automatiquement —
  l'utilisateur peuple explicitement le cache.
* Le bilan en fin de conversion pointe désormais aussi vers
  `noto-cjk pull` avec les commandes concrètes pour
  chaque variante + le status actuel du cache.
* Aucune régression : 94 tests, tous verts.

== v2.3.24.12 — 2026-04-26

**Meilleure détection de la couverture de la police** — corrige
une substitution trop agressive de v2.3.24.10 qui transformait
en `?` des caractères valides (Cyrillique Привет, Grec Καλημέρα,
Hébreu שלום, dingbats simples ✓ ✗ ★) alors que DejaVu Sans (la
police embarquée par défaut) pouvait parfaitement les rendre.

supposant Type1 Helvetica/Courier — mais le converter utilise
en fait DejaVu Sans TrueType embarquée par défaut, qui couvre
une plage de codepoints bien plus large. Le nouveau pipeline
interroge directement la police active via la nouvelle méthode
`TrueTypeFont#has_glyph?(char)` de `pdf v0.3.5`, et ne
retombe sur la table WinAnsi statique que pour les polices Type1
(rare — uniquement quand DejaVu est désactivée dans le thème).

* Bump dep `pdf` à `~> 0.3.5`.
* `Converter#safe_text(text, font_name = @fn_body)` prend
  désormais le nom de la police et route la couverture
  par-caractère via la requête TrueType `has_glyph?`.
* `font_object_for(font_name)` extrait du `case` dupliqué de
  `set_font` — source unique de vérité pour résoudre un nom de
  police vers son instance `PDF::Fonts::Base`.
* Message d'avertissement mis à jour : « caractère « X » (U+NNNN)
  sans glyphe dans la police active » (avant : « absent de
  WinAnsi »).
* 94 tests, toujours verts, aucune régression.

== v2.3.24.10 — 2026-04-26

Met fin aux carrés tofu silencieux pour les caractères hors plage
WinAnsi. Les polices Type1 standard (Helvetica, Courier — défauts
du converter) ne couvrent que ~220 codepoints (ASCII + Latin-1 +
quelques extras Windows-1252). Tout le reste — emojis (✅ ❌ 🔴),
dingbats (✓ ✗ ★), idéogrammes CJK, etc. — sortait jusqu'ici en
rectangles vides sans aucun avertissement à l'auteur.

Le correctif :

* Nouveau module `AsciidoctorPDF::WinAnsi` avec les helpers
  `representable?(char)` et `sanitize(text) { |char| … }`.
* Nouvelle méthode `Converter#safe_text(text)` qui substitue tout
  caractère hors WinAnsi par `?` et émet un avertissement dédupliqué

== v2.3.24.6 — 2026-04-23

Préserver la propriété insécable de `&nbsp;` / `&#160;` lors du
wrap.

Le correctif de la v2.3.24.5 normalisait tout espace insécable en
espace ASCII *avant* le wrap, ce qui éliminait les tofus mais
supprimait aussi la propriété « ne pas couper » de la séquence —
les utilisateurs qui font un usage intensif de `&nbsp;` pouvaient
voir un saut de ligne précisément là où ils l'avaient écrit pour
l'empêcher.

Le pipeline devient :

* Les entités HTML `&#160;` et `&nbsp;` sont décodées vers le
  vrai caractère **U+00A0** (espace insécable). Un U+00A0 déjà
  présent dans l'entrée est conservé tel quel.
* `wrap_text` casse uniquement sur l'espace ASCII (la regex
  `/\s/` ne matche pas U+00A0 en Crystal), donc une paire de
  mots jointe par U+00A0 reste sur la même ligne.
* Juste avant chaque `page.text` (dans `draw_text_run` du
  converter et dans `InlineRenderer.render_line`), U+00A0 est
  remplacé par un espace ASCII dans la chaîne dessinée — le
  PDF est visuellement propre que la police active ait ou non
  un glyphe NBSP drawable.

Résultat : le rendu visuel est identique à la v2.3.24.5 (pas de
tofu), mais les sauts de ligne respectent maintenant les espaces
insécables de l'auteur.
