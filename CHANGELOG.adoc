== v2.3.24.80 — 2026-06-03

=== Added

* **`hyph install <lang> --force` bypasses license-undeclared
  exclusion.** Languages in `EXCLUDED_LANGS` (currently
  `mn-cyrl-x-lmc`, `ro`) can now be installed if the user
  explicitly accepts the legal risk by passing `--force`
  (or `-f`). Without `--force`, the previous refusal stays in
  place (exit `10`).

  The `--force` flag thus widens its meaning: it now signals
  “I accept all risks” — including ambiguous licensing, in
  addition to its historical role of overwriting an existing
  install.

  With `--force` enabled:

  0. Warning on `stderr` recalling the recorded reason.
  0. Download from the effective mirror (GitHub by default,
     see below).
  0. SHA-256 verification **still active** against the hash
     stored in `EXCLUDED_LANGS` — an attacker serving a
     malicious file would still be detected.

  Associated refactor: `EXCLUDED_LANGS` is no longer a plain
  `Hash(String, String)` but a `Hash(String, ExcludedEntry)`
  (new record) with `reason`, `url`, `sha256`, `size`. The
  symmetry with `ManifestEntry` enables the same integrity
  check.

* **HTTP 301/302/303/307/308 redirect-following in
  `hyph install`.** New private function
  `http_get_following_redirects` (up to 5 hops) resolving
  `Location` headers (including relative ones via
  `URI#resolve`). Crystal's stdlib `HTTP::Client.get` does
  not follow redirects automatically — and CTAN mirrors
  `mirrors.ctan.org` typically respond with 307 to a
  geographic mirror.

=== Changed

* **Effective download URL switches to the GitHub mirror by
  default.** The manifest still references the canonical
  CTAN URL (for documentation purposes), but `hyph install`
  rewrites that URL to point to the stable GitHub mirror:
  `https://raw.githubusercontent.com/hyphenation/tex-hyphen/master/hyph-utf8/tex/generic/hyph-utf8/patterns/tex/`.
  The main CTAN mirror (`mirrors.ctan.org`) now returns
  `404` on these paths (observed in this session: redirect
  to `ctan.mines-albi.fr` which returns 404). Users can
  override via env vars `HYPH_MIRROR` or `CTAN_MIRROR`, or
  via `--from` explicit.

== v2.3.24.79 — 2026-06-03

=== Added

* **True multi-line CJK justification.**
  `ParagraphComposer.tokenize` now detects segments containing
  CJK characters (≥ U+3000) and delegates to a dedicated
  `tokenize_segment_with_cjk` helper which splits EACH CJK
  character into a standalone `Box`, separated by a thin
  `Glue` (`width = 0`, `stretch = char_w × 0.5`,
  `shrink = 0`) between two consecutive CJK chars.

  These thin Glues serve two purposes:

  0. **Legal break-point** that `compose_knuth_plass` uses to
     wrap long CJK paragraphs onto multiple lines. Before this
     change, lacking break-points (CJK paragraphs have no
     ASCII space to naturally act as Glue), a CJK paragraph
     stayed unavoidably on a single line — the composer
     couldn't break it, the user saw it extending past the
     margin.
  0. **`Tc` stretch support.** Knuth-Plass stretches these
     Glues in proportion to each line's `adjustment_ratio`;
     the renderer recomputes the same value via
     `extra_per_cjk_glyph = (target_w - natural_w) /
     (n_cjk - 1)` and emits it via
     `page.text(..., char_spacing:)`.

  NO Glue between a CJK char and an adjacent Latin char: the
  Sino-Japanese convention writes `日本2026年` glued; breaking
  here would be a typographic violation.

  Composer-side corollaries:

  - `finalize_line` and `finalize_kp_line` distinguish a
    “space” Glue (`width > 0`, Latin) from a “thin” Glue
    (`width == 0`, CJK). Only space Glues contribute to
    `n_spaces` and trigger a leading space on the following
    Box — thin CJK Glues introduce no space character in the
    rendered output.
  - The measurement block in `wrap_segments` now accepts an
    isolated CJK char: it uses `font_cjk.string_width` when
    the char is ≥ U+3000 and recognized by the CJK font, else
    `font.string_width` (main Latin font). Without that fix,
    each CJK char would be measured at 0 by Noto Sans Latin
    → phantom-width tokens, underestimated `natural_w`,
    badly-broken lines.
  - The block is now captured as a named `Proc`
    (`&measure : ...`) rather than as implicit `yield`.
    Crystal forbids `yield` inside a Proc literal —
    refactor needed so `tokenize_segment_with_cjk` can
    forward the block to a sub-lambda `flush_latin`. (Bonus:
    `Array(Char)` instead of `String::Builder` for the Latin
    buffer, because `String::Builder.to_s` may only be called
    once and `flush_latin` is called multiple times per
    paragraph.)

  Renderer-side corollaries (`render_segment_line`):

  - `seg_w` computation detects CJK chars and splits by run
    to use `font_cjk` on CJK, `font` on Latin. Without it,
    `seg_w ≈ 0` for isolated CJK chars and `current_x`
    wouldn't advance between two adjacent CJK segs: all
    glyphs piled up at the same visual position ≈ 36.
  - The “non-badge” branch (word-by-word) propagates the
    same correction on the `part_w` measured between
    consecutive `draw_text_run` calls.
  - The CJK `Tc` advancement is now added to `current_x`
    AFTER the seg's draw: `current_x += n_cjk_in_seg ×
    extra_per_cjk_glyph` to follow the PDF engine which
    translates its own cursor by `glyph_w + Tc` after each
    glyph.

  Verification on a long Chinese paragraph (~50 Han
  characters + Knuth-Plass + Latin algorithm):

  - The composer correctly breaks between two CJK chars
    (transition `测` / `试`).
  - Both resulting lines are justified to the right edge
    (xMax=559.28 = target_w).
  - 259/259 specs green. Ameba clean. The J4.A fix
    preserved (“186260).” still glued).

== v2.3.24.78 — 2026-06-03

=== Removed

* **Languages with undeclared licenses removed from manifest
  (`mn-cyrl-x-lmc`, `ro`).** Manifest size goes from 87 to
  **85 languages**. The two removed entries carried
  `license: "Unknown"` because their upstream source header
  declares no free-software grant (`NONE` for `mn-cyrl-x-lmc`,
  `[None]` for `ro`). Distributing these patterns via our
  manifest would put our users in a legally ambiguous spot —
  the ALOLI convention being to distribute only
  clearly-licensed free software, we prefer to exclude them.

  New constant `EXCLUDED_LANGS : Hash(String, String)` in
  `manifest.cr` maps each excluded language code to a
  diagnostic message in English (lingua franca of free-software
  licensing discussions). The `hyph install <lang>`
  sub-command consults this table BEFORE the manifest: if the
  language is listed and the user did not pass `--from`,
  install is refused with the explanatory message and exit
  code `10` (manifest missing).

  Users can still install these languages manually after
  independently verifying the legal situation:

  [source,bash]
  ----
  asciidoctor-pdf hyph install ro \
    --from https://example.org/hyph-ro.tex \
    --sha256 <HASH_THEY_COMPUTED>
  ----

  `${XDG_CACHE_HOME:-~/.cache}/asciidoctor-pdf/hyph-available.json`

  Source URL configurable via `HYPH_MIRROR` or `CTAN_MIRROR`;
  default is the GitHub API (JSON listing); naive HTML regex
  fallback for classic CTAN mirrors.

  manifest + exit `0` (CI-usable). 16 unit + integration
  specs via `Process.run` against the binary (flag parsing,
  cache reads, fallback, output formats).

== v2.3.24.75 — 2026-06-03

=== Added

* **CJK justification via `Tc` (“両端揃え / 两端对齐”).**
  Pure Chinese / Japanese / Korean paragraphs — those
  containing no ASCII space — are now justified to the right
  edge by stretching the space between each glyph via the
  native PDF `Tc` operator (Character Spacing,
  ISO 32000-1 § 9.3.2), per the canonical Sino-Japanese
  typographic convention.

  Detection: the line contains no ASCII space (`n_spaces ==
  0`), `target_w` is set, `font_cjk` is loaded, and at least 2
  CJK glyphs are recognized by `font_cjk.has_glyph?`.
  Justification stays active even when the received `align` is
  `left` (case of single-line CJK paragraphs, hence “last
  paragraph line” from the composer's view — explicit
  exception to the “last line left-aligned” rule, to honor the
  CJK convention).

  Computation: `extra_per_cjk_glyph = (target_w - natural_w)
  / (n_cjk - 1)`. Guardrail at 75 % of a typical CJK glyph
  width (`中`) to prevent pathologies (2 glyphs alone on a
  very wide line). 75 % is more permissive than the 50 % of a
  first POC — the CJK convention routinely accepts stretches
  up to ~100 %, and the cap was blocking legitimate short
  Japanese lines.

  Concurrent fix to `natural_w` computation: the main font
  (Noto Sans Latin) doesn't contain CJK glyphs and returned
  0 / ε for them, underestimating `natural_w` and skewing all
  mixed-justify computations. We now delegate to
  `text_with_emoji_segments` for per-font segmentation, then
  sum widths with the right font (`font_cjk` for `:cjk` runs,
  `font` for `:text` runs).

  `draw_text_run` accepts an optional `cjk_char_spacing`
  parameter (default `0.0`) which propagates to
  `page.text(..., char_spacing:)` in the `:cjk` branch. The
  Crystal-side cursor advancement compensates the PDF
  engine's accumulated `Tc`: `cursor += string_width + (n - 1)
  × cjk_char_spacing` so the cursor points to the VISUAL end
  of the last glyph (the `Tc` added by PDF after the last
  glyph is invisible — automatically reset by the `pdf` shard
  at the end of `page.text`).

  Visual verification (`/tmp/cjk-test.adoc`):

  - Before: Chinese line xMax=476 (far from right edge 559),
    Japanese line xMax=386.
  - After: Chinese line xMax=559.28 (= right edge `target_w`),
    Japanese line xMax=559.28 (= right edge). Perfectly
    justified.

  Acknowledged limitation: the current
  `ParagraphComposer.tokenize` treats each CJK string as a
  single Box (split on ASCII space only), forcing long CJK
  paragraphs to a single line (composer can't break). True
  multi-line CJK justification would require tokenize-level
  per-glyph splitting with soft Glues between each — major
  refactor planned if real need arises. Current `Tc` rail
  covers most practical cases (a short paragraph in Chinese
  or Japanese).

== v2.3.24.74 — 2026-06-03

=== Added

* **J4.B: native PDF emission for justified text — `TJ` for
  composite fonts, `Tw` for simple fonts.** Bumped
  `aloli-crystal/pdf` dependency from `~> 0.6.4` to `~> 1.2`,
  which now exposes `page.text(word_spacing:, char_spacing:)`
  (`Tw` + `Tc` operators, ISO 32000-1 §§ 9.3.3 and 9.3.2) and
  `page.text_positioned(runs)` (`TJ` operator, § 9.4.3) with
  automatic font-type detection via `page.composite_font?`.

  Implementation in `render_segment_line`:

  0. For each non-badge segment with `extra_per_space > 0`:
     try the native path via the new helper
     `try_native_justified_text`.
  0. If the segment is natively renderable (no country flag,
     no emoji, no CJK run — checked by `native_renderable?`):

     - **Simple font (Type1, AFM)**: `page.text(content,
       word_spacing: extra)` emits native `Tw`. The PDF engine
       applies the extra to every `0x20` byte.
     - **Composite font (TrueType, CID — our default with Noto
       Sans)**: `Tw` does not apply (ISO 32000-1 § 9.3.3:
       “word spacing shall not apply to occurrences of the
       byte value 32 in multiple-byte codes”). Instead we emit
       `TJ` with explicit between-word offsets:
       `[word1, " ", -extra_tj, word2, " ", -extra_tj, word3] TJ`.
       The negative delta in text space units translates the
       cursor rightward (inverse PDF convention).
  0. If the segment contains an inline-mixed element (flag,
     emoji, CJK run): fall back to manual word-by-word
     advancement via `draw_text_run` — behavior preserved.

  Quantitative verification on the test PDF
  (`/tmp/codespan-test.adoc`): 58 `TJ` operators now emitted
  (was 0), 30 % `Tj` operators saved (~200 → 139). Visual
  rendering is strictly pixel-identical — the optimization
  happens at the PDF content stream level, not glyph placement.

  Typographic bonus for CJK: the `TJ` path is the
  infrastructure needed for upcoming CJK justification (`Tc`
  character-spacing stretching all glyphs rather than spaces,
  the canonical “中文两端对齐” convention).

=== Documentation correction

* **Rectified the v2.3.24.73 note about native `Tw`.** The
  previous changelog claimed the `aloli-crystal/pdf` shard
  didn't support `Tw`. That was a false negative on my side —
  a grep against `lib/pdf/` (installation frozen at `0.6.4`)
  missed the new methods added in `1.1.0` and `1.2.0`. The
  dependency bump above restores ground truth: `Tw` / `Tc` /
  `TJ` are all three available in `pdf 1.2.0`, with automatic
  font-type detection to emit the right operator.

== v2.3.24.73 — 2026-06-03

=== Fixed

* **J4: residual visual gap between codespan and clinging
  punctuation.** Symptom: `(ex : `186260`).` visibly rendered
  as `(ex : `186260` ).` with a ~1-2 pt space before the
  closing parenthesis. Same for ``prepare_rescue`,`` which
  rendered as ``prepare_rescue` ,``.

  Cause: the “badge” branch of `render_segment_line` (mark /
  codespan / kbd / button segments) drew the text in one shot
  then added `extra_per_space * count(' ')` to `current_x`.
  The next segment (punctuation) therefore started
  `extra_per_space` points too far right.

  Fix: when the segment carries a leading space prefix (Glue
  rendered by the composer) AND we're in justify mode, the
  leading space is now stretched **BEFORE** the draw — we
  advance `current_x` by `prefix_w + extra_per_space`, then
  draw `seg.text[1..]` (without the prefix). At the end of
  the draw, `current_x` matches exactly the visual end of the
  badge text; the following punctuation glues naturally. The
  background rectangle (`badge_x`) is also offset by
  `extra_for_leading` to stay aligned with the actually-drawn
  text.

  Verification: `pdftotext -bbox-layout` now extracts
  `186260).` as a single word (before: `186260` and `).`
  separated with 4.72 pt gap).

=== Documented

* **J4.B (native PDF `Tw`) deferred.** Ideal would have been
  relying on PDF's `Tw` operator (Word Spacing,
  ISO 32000-1 § 9.3.3), which applies the extra to *all*
  ASCII spaces of a `Tj` string at the PDF engine level — no
  position calculation Crystal-side. But the `pdf` shard
  (aloli-crystal/pdf) doesn't expose it currently: it does
  word-by-word drawing with a `word_spacing` property on its
  Fragments (cf. `lib/pdf/src/pdf/text/formatted/box.cr:310`).
  Adding native `Tw` would require extending the `pdf` gem —
  separate work. The J4.A fix above achieves the same visual
  result via manual cursor advancement.

== v2.3.24.72 — 2026-06-03

=== Changed

* **J3: Knuth-Plass becomes the default composition engine.**
  We stay on the 4th digit for now (`24.71` → `24.72`) —
  alignment with the Ruby asciidoctor-pdf 2.3.24 gem
  maintained, pending an explicit decision on whether this
  shard — which is progressively diverging from the gem's
  behavior (native Knuth-Plass, Liang hyphenation, custom
  CLI, etc.) — should switch to autonomous versioning (3rd
  digit bump or even a new SemVer scheme).

  `ParagraphComposer.compose_knuth_plass` implements the
  Knuth & Plass algorithm (*Breaking Paragraphs into Lines*,
  Software Practice & Experience vol. 11, p. 1119-1184, 1981),
  the historical TeX algorithm:

  0. Identify legal breakpoints (each `Glue` after a `Box`,
     each non-infinite `Penalty`, end of paragraph).
  0. For each candidate breakpoint B, dynamic programming over
     all preceding breakpoints A: compute the `badness` of the
     A→B line (`100 · |adjustment_ratio|³`, TeX formula), the
     `demerits` (`(1 + badness)² + penalty² +
     double_hyphen_demerits`), memoize the optimal path.
  0. Backtrace to reconstruct the optimal sequence.
  0. Graceful fallback on first-fit if no admissible path
     (pathological paragraph: word too long, target_w too small).

  Visible benefits: balanced lines (similar `adjustment_ratio`
  across the paragraph), exploitation of J2 hyphenation
  Penalties (K-P prefers hyphenation over extreme stretching),
  fewer rivers, double-hyphen penalty (10000 demerits) to
  avoid two consecutive hyphen-ended lines.

* **Removed the `max_extra_factor = 2.5` guard** in
  `render_segment_line`. This heuristic silently fell back to
  `left` alignment when first-fit's `extra_per_space` exceeded
  2.5× a normal space's width — a band-aid on first-fit's bad
  behavior of maxing out each line without looking ahead.
  With Knuth-Plass, stretching stays reasonable by construction
  (K-P minimizes badness² globally), and the user always gets
  the justification their theme requests. Rare pathological
  paragraphs (single overlong word on a wide page) now produce
  visible-but-correct stretching rather than a silent
  fallback to `left` that broke document appearance.

== v2.3.24.71 — 2026-06-03

=== Added

* **J2: `Hyphenation` module (Liang algorithm).** New
  implementation of Liang's pattern-based hyphenation
  (Franklin Mark Liang, *Word Hy-phen-a-tion by Com-pu-ter*,
  Stanford thesis, 1983) — the historical TeX algorithm.
  Three sub-modules: `Trie` (Liang pattern storage),
  `Hyphenator` (main algorithm with `LEFT_MIN = 2`,
  `RIGHT_MIN = 3` defaults, exceptions support), `Loader`
  (cascade project / XDG / embedded, class-level cache,
  `en` → `en-us` and `de` → `de-1996` aliases).

* **7 Liang patterns embedded at build via `read_file`**:
  FR (~ 30 KB), EN-US (~ 33 KB), DE-1996 (~ 268 KB),
  ES (~ 42 KB), IT (~ 5 KB), PT (~ 5 KB), NL (~ 86 KB).
  Total: ~ 470 KB embedded in the binary. Sources: CTAN
  (hyph-utf8 package). Licenses vary per file (MIT /
  LPPL-1.3 / Knuth-permissive / BSD-3-Clause) — see
  `src/asciidoctor_pdf/hyphenation/manifest.cr`.

* **Manifest of known CTAN languages**: URL, expected SHA-256,
  size, license, `embedded` flag per language. 7 entries
  initially (the embedded ones); to be extended toward the
  ~80 hyph-utf8 languages in a later iteration.

* **Integration in `ParagraphComposer.tokenize`**: composer
  takes an optional `hyphenator` parameter. Each word whose
  alphabetic core is at least `LEFT_MIN + RIGHT_MIN` letters
  long is fragmented into sub-Boxes connected by `Penalty`
  (cost 50, flagged, hyphen width). Head/tail punctuation
  stays glued to first/last syllable. In `compose_first_fit`
  (J1) Penalties are ignored (rendering identical to
  monolithic word) — value comes at J3 with Knuth-Plass.

* **Document language detection** in `Converter`: AsciiDoc
  `:lang:` attribute. Stored in `@document_lang`, used by
  `wrap_segments` to resolve the hyphenator via
  `Hyphenation::Loader.for(@document_lang)`. No implicit
  default: if `:lang:` is not set, no hyphenation (graceful
  composition).

* **CLI `hyph` sub-command**
  (`bin/crystal-asciidoctor-pdf hyph <sub>`). 7 sub-commands
  matching `doc/CLI_HYPH_SPEC.adoc` and ALOLI conventions:
  `list`, `available`, `install`, `remove`, `update`, `show`,
  `help`. Numbered exit codes (0 / 2 / 3-10) for scripting.
  `tlmgr` inspiration: no automatic runtime download, always
  explicit action, mandatory SHA-256 verification.

  5 on `ParagraphComposer.tokenize` × hyphenator integration.

== v2.3.24.70 — 2026-06-03

=== Fixed

* **Codespan background bled over the leading space.** When the
  `ParagraphComposer` renders a codespan (or kbd / button / mark)
  preceded by a justification Glue, the segment carries a leading
  ASCII space prefix (` code` rather than `code`). The badge's
  background rectangle covered that prefix, making the gray
  background overflow to the left of the first real character.
  The rectangle is now offset by a `leading_space_w` computed in
  the current font: the background starts at the first character
  and ends at the last, the leading space stays white and plays
  its visual separator role.

* **Phantom space inserted between `` `code` `` and clinging
  punctuation (`)`, `.`, `,`, `;`, `:`, `!`, `?`, `]`, `}`, `»`).**
  Two causes in cascade:
+
  0. `ParagraphComposer#tokenize` was injecting an artificial
     Glue between two Boxes from contiguous segments
     (“bug-for-bug compatible” with the old `wrap_segments`).
     That branch is removed: asciidoctor's HTML already contains
     the necessary spaces in segment texts, we mustn't fabricate
     any. Segments without an inter-frontier space are now
     rendered contiguously (`<strong>foo</strong>bar` → `foobar`).
  0. `render_segment_line` was adding `codespan_padding_x` (and
     kbd / button / mark equivalents) to `current_x` after each
     badge to prevent the next word from overlapping the badge's
     background. That padding is now conditional: it's skipped
     when the next segment starts with a space (separation
     already provided) or with clinging punctuation. Before:
     `` `code` ). `` (visible). After: `` `code`). ``.

  Dedicated spec in `paragraph_composer_spec`: new case
  “preserves the `)` glued after a codespan” validating the
  expected token sequence for `(ex : ` `` `code` `` `)`.

  Note: a residual gap of ~1-2 pt may persist on heavily

== v2.3.24.69 — 2026-06-03

=== Fixed

* **French NBSP wiped out before reaching the wrapper.** The
  whitespace-normalization regex in `InlineRenderer.parse`
  (`gsub(/\s+/, " ")`) treated U+00A0 (NBSP) as ordinary
  whitespace (PCRE2 in Unicode mode classifies NBSP under `\s`).
  Result: every NBSP freshly inserted by
  `apply_french_typography` (before `:`, `;`, `!`, `?`, `»`) was
  immediately replaced with an ASCII space one step later, and
  `wrap_segments` would happily break the line on it. The
  Imprimerie nationale rule wasn't honored — `deploy : il`
  could be split into `deploy` on one line and `: il` on the
  next.

  The regex is now `gsub(/[^\S\x{00A0}]+/, " ")` — “all
  whitespace EXCEPT NBSP”. NBSPs are now preserved through the
  pipeline and reach `wrap_segments` (which already only split
  on strict ASCII space).

=== Added

* **Structured paragraph composition engine
  (`ParagraphComposer`).** Refactor of `wrap_segments` which
  now delegates to a new module
  `src/asciidoctor_pdf/paragraph_composer.cr` modelling the
  text stream as TeX-style tokens: `Box` (a word or NBSP-bound
  group, fixed non-breakable width), `Glue` (elastic space,
  legal break-point), `Penalty` (forced/forbidden/conditional
  break). The `compose_first_fit` algorithm faithfully
  reproduces the historical greedy behavior — 217/217 specs
  pass. Immediate benefit: NBSP non-breakability is guaranteed
  by construction (NBSPs are absorbed into the neighboring Box
  and can no longer be break-points).

  Reference: Knuth & Plass, *Breaking Paragraphs into Lines*,
  Software Practice & Experience, vol. 11, p. 1119-1184, 1981.

  This structure is the typed foundation for the upcoming
  milestones: J2 (Liang hyphenation patterns for FR/EN/DE/ES/
  IT/PT/NL embedded + `hyph` CLI sub-command for additional
  languages), J3 (Knuth-Plass algorithm — global paragraph
  optimization minimizing badness), J4 (PDF output via the
  native `Tw` operator from ISO 32000-1 § 9.3.3).

=== Documentation

* **`doc/CLI_HYPH_SPEC.adoc`**: specification of the upcoming
  `hyph` CLI sub-command (7 sub-commands: `list`, `available`,

== v2.3.24.7 — 2026-04-23

Extend non-breaking-space handling to every renderer that was still
emitting raw HTML entities or raw U+00A0 characters.

* **Document title** (`@document_title`) is now decoded through

* **Cover page**: `render_title_page` now calls `draw_text_run`

* **Floating titles, TOC entry titles, table captions**: same

Net effect: `{nbsp}` and `&nbsp;` in *any* author-facing text —

== v2.3.24.6 — 2026-04-23

Preserve the non-break property of `&nbsp;` / `&#160;` in wrap.

The v2.3.24.5 fix normalised every non-breaking space to an ASCII
space *before* wrap, which eliminated the tofu glyphs but also
dropped the "do not break" property of the sequence — users relying
heavily on `&nbsp;` could see a line break exactly where they had
written one to prevent it.

Pipeline is now:

* HTML entities `&#160;` and `&nbsp;` decode to the actual
  character **U+00A0** (non-breaking space). A bare U+00A0 that
  was already in the input is kept as-is.
* `wrap_text` splits on ASCII space only (regex `/\s/` does not
  match U+00A0 in Crystal), so a word pair joined by U+00A0 stays
  on the same line.
* Just before each `page.text` call (`draw_text_run` in the
  converter and `InlineRenderer.render_line`), U+00A0 is replaced
  by an ASCII space in the drawn string — the PDF is visually
  clean regardless of whether the active font has a drawable
  NBSP glyph.

Net effect: the visual result is identical to v2.3.24.5 (no tofu)
but line breaks now honour the author's non-breaking spaces.

== v2.3.24.5 — 2026-04-23

Broader flag rendering plus a handful of white-space glyph fixes.

* **Flags in paragraphs, admonitions and lists** too — not just in
  tables. `draw_text_run` is now called from `convert_paragraph`
  (via `InlineRenderer.render_line`), `render_admonition`,
  `convert_dlist` and `render_list`. Any regional-indicator pair
  inside body text now renders as an actual colour SVG flag.
* **Fix tofu glyphs from `<br>`**: the inline renderer translated a
  `<br>` into a literal `\n` in the draw buffer, which showed up as
  a tofu box since Type1 fonts have no glyph for newline. It now
  emits an ordinary space; hard line breaks are effectively
  treated as word separators. A proper multi-line layout for
  `<br>` is left for a future pass.
* **Fix tofu glyphs from soft newlines**: the HTML generated by
  AsciiDoctor preserves line breaks from the source inside
  paragraphs. The inline renderer and `strip_inline_markup` now
  collapse any run of whitespace into a single space before the
  text is drawn.
* **Fix non-breaking-space tofu**: `&#160;`, `&nbsp;` and bare
  U+00A0 are now normalised to an ordinary space (the non-break
  property is lost, which is an acceptable trade-off given Type1
  standard fonts don't always expose a drawable NBSP glyph).
* **Dependency bump**: `pdf` → uses v0.3.3 via `~> 0.3`,
  which adds a document-scoped cache of `SVG::Parser` instances so
  repeated flags on the same document are parsed only once.

== v2.3.24.4 — 2026-04-23

Real country flags in table cells, via a new SVG rendering pipeline.

  SVG flags from lipis/flag-icons embedded at compile time.

== v2.3.24.3 — 2026-04-23

Layout and typography fixes observed on real-world documents.

* **Admonitions** (NOTE, TIP, IMPORTANT, WARNING, CAUTION): the label
  now has a proper gap before the text. Previously the label fit in a
  fixed 60 pt slot regardless of its rendered width, which made long
  labels like `IMPORTANT` visually collide with the first word of
  the message.
* **Section titles**: long titles are now wrapped across multiple
  lines instead of being rendered past the right margin (and
  truncated). Uses the existing `wrap_text` helper with the heading
  font.
* **Table cells**: words that do not fit in their column (typical
  for country names in narrow proportional columns, e.g. `Allemagne`
  or `Pays-Bas`) are now broken into sub-chunks. Break priority:
  internal hyphens (`Pays-` + `Bas`), camelCase boundaries, then a
  per-character fallback. No visual overflow into the neighbouring
  column any more.
* **Default body font size**: lowered from 10.5 pt to 10 pt. Mostly
  cosmetic — makes dense tables fit better on A4 without changing
  the heading hierarchy.
