== v2.3.24.65 — 2026-06-02

=== Added

* **Inline code rendering (codespan).** New `codespan_*` theme
  category ported from the `asciidoctor-pdf` Ruby spec 2.3.24 :
  grey background + optional border + text colour + configurable
  padding behind `` `text` `` inline segments. Before this port,
  inline code was rendered in mono font but without any visual
  framing — `_default.yml` looked like ordinary text.

* **French typography (`x-` extension).** New theme property
  `x_french_typography` (`true` by default in the `fr` theme,
  `false` elsewhere). When enabled, the converter replaces the
  regular space before `:`, `;`, `!`, `?`, `»` and after `«`
  with a non-breaking space U+00A0 — follows the Imprimerie
  nationale typography rules and avoids line breaks splitting
  two-part punctuation.
+
Code blocks (`[source,...]`, ` ```), literal blocks and
attributes (style, language) are **preserved** since they do
not go through the inline parser pipeline.

* **Inline markup preserved in list items.** Previously
  `render_list` passed each item's text through `strip_inline_markup`
  + raw `draw_text_run` — result : every italic, bold, inline code,
  link, etc. was *stripped* and rendered as flat text. The full
  pipeline (`InlineRenderer.parse` + `wrap_segments` +
  `render_segment_line`) is now used, identical to paragraphs.
  Justify also applies to long items (non-terminal lines).
+
Exposed theme properties (defaults match upstream asciidoctor-pdf) :
+
[cols="2,2,3"]
|===
| Property | Default | Effect

| `codespan_background_color`
| `f5f5f5`
| Very light grey background behind the code

| `codespan_border_color`
| _empty_
| Border disabled by default

| `codespan_border_width`
| `0.0`
| Same

| `codespan_font_color`
| _empty_
| Inherits the current text colour

| `codespan_padding_x`, `codespan_padding_y`
| `2.0`, `1.0`
| Space around the text (points)
|===

* **Justified paragraphs by default** (`base_text_align: "justify"`).
  Rendering distributes the unused space on a line between
  inter-word spaces ; the last line of a paragraph stays
  left-aligned so an orphan line isn't stretched. Configurable
  through the `base_text_align` theme property (values: `"left"`,
  `"center"`, `"right"`, `"justify"`). Conforms to upstream
  asciidoctor-pdf where `base_align: justify` is the default.
+
Algorithm : for every line except the last, compute the natural
width of segments, count internal spaces, then distribute
`(target − natural) / n_spaces` after each segment proportionally
to how many spaces it contains. Simple approximation (spaces
*between* segments are stretched, those internal to a single
segment stay fixed) — sufficient for typical paragraphs with light
markup (italic, inline code, etc.).

=== Changed

* `crystal-asciidoctor` dependency bumped to **`~> 2.0.26.6`** —
  hybrid `[source,LANG]` + `\`\`\`` blocks (form accepted by
  Asciidoctor Ruby in Markdown compatibility mode) now properly
  carry the `language` attribute. As a result : syntax highlighting
  + grey background + `language-LANG` class are applied just like
  for the canonical `[source,LANG] ----` form.

== v2.3.24.64 — 2026-06-02

=== Changed

* **CJK fonts now render natively.** Bumped the `pdf` dependency to
  `~> 0.6.4`, which adds native OpenType/CFF (`.otf`) subsetting and
  embedding. All Noto CJK fonts ship as `.otf`, so until now they
  triggered `UnsupportedFontFormat` and CJK characters fell back to
  `?`. With pdf 0.6.4 a cached Noto CJK font is loaded lazily on the
  first CJK character and embedded as a `CIDFontType0` subset — the
  ideographs render and the text is extractable.
* The lazy `font_cjk` accessor comments were updated : the
  `rescue UnsupportedFontFormat` is now a safety net for a genuinely
  corrupt / exotic font, no longer the expected path for CJK.

=== Fixed

* Integration spec `non_winansi_chars_spec` no longer hard-codes the
  obsolete "CJK → `?`" expectation. It now asserts the behaviour
  conditional on a Noto CJK font being present in the cache (rendered,
  no `?`) or absent (`?` fallback). The integration text-extraction
  helper's Identity-H caveat is documented (it reads raw GIDs, not
  ToUnicode, so it cannot reproduce exact CJK text — only the
  presence / absence of the `?` substitution).

== v2.3.24.63 — 2026-06-02

== v2.3.24.60 — 2026-06-01

=== Fixed

* **Truly lazy CJK font loading.** In v2.3.24.59 the `font_cjk`
  accessor was lazy, but `text_with_emoji_segments` called it on
  the very first text run of the document — which triggered the
  `UnsupportedFontFormat` warning (`.otf` CFF unsupported) for
  *every* document, including those with no CJK character at all.
* Now `font_cjk` is only consulted for *plausibly CJK* characters
  (`ord >= 0x3000` — start of the CJK Symbols and Punctuation
  block). Below that we are on Latin or European typographic
  punctuation (curly apostrophe `'`, em dash `—`, ellipsis `…`,
  etc.) which the CJK font would not cover anyway — no point
  loading it just to find that out. As a result, European
  CJK-free documents no longer emit the warning.
* The warning is still emitted **once** when an actual CJK
  character (Japanese, Chinese, Korean, ...) is encountered in
  the document.

== v2.3.24.12 — 2026-04-26

**Better font coverage detection** — fixes a v2.3.24.10
over-aggressive substitution that turned valid characters
(Cyrillic Привет, Greek Καλημέρα, Hebrew שלום, simple dingbats
✓ ✗ ★) into `?` even when DejaVu Sans (the default embedded

fonts (rare — only when DejaVu is intentionally disabled in the
theme).

* Bump dep `pdf` to `~> 0.3.5`.
* `Converter#safe_text(text, font_name = @fn_body)` now takes
  the font name and routes per-character coverage through the
  TrueType `has_glyph?` query.
* `font_object_for(font_name)` extracted from the previous
  duplicated `case` in `set_font` — single source of truth for
  resolving a font name to its `PDF::Fonts::Base` instance.
* Warning message updated : « caractère « X » (U+NNNN) sans
  glyphe dans la police active » (was : « absent de WinAnsi »).
* Tests still all green : 94 examples, no regressions.

== v2.3.24.10 — 2026-04-26

Stops the silent tofu boxes for characters outside the WinAnsi
encoding range. Type1 standard fonts (Helvetica, Courier — the
defaults of this converter) only cover ~220 codepoints (ASCII +
Latin-1 + a few Windows-1252 extras). Anything beyond — emojis
(✅ ❌ 🔴), dingbats (✓ ✗ ★), CJK ideographs, etc. — used to
render as empty rectangles with no warning to the author.

The fix :

* New `AsciidoctorPDF::WinAnsi` module with `representable?(char)`
  and `sanitize(text) { |char| … }` helpers.
* New `Converter#safe_text(text)` substitutes every non-WinAnsi
  character with `?` and emits a deduplicated warning to STDERR
  («  Avertissement : caractère « ✅ » (U+2705) absent de WinAnsi,
  remplacé par « ? » dans le PDF. »). One warning per character
  per conversion — no spam if the same emoji appears N times.
* `draw_text_run` runs every text run through `safe_text` before
  passing it to `page.text`.
* New tests : 11 unit specs for `WinAnsi`, 2 integration specs
  proving emojis no longer crash the converter and pure-WinAnsi
  text is left untouched. **93 tests total, all green.**

This is a conservative fix that removes the silent failure mode.
The next step (planned as a separate shard) is `emojis`,
which will render real **coloured emojis** as embedded SVG glyphs
(same pattern as `flags` for country flags).

== v2.3.24.6 — 2026-04-23

Preserve the non-break property of `&nbsp;` / `&#160;` in wrap.

The v2.3.24.5 fix normalised every non-breaking space to an ASCII
space *before* wrap, which eliminated the tofu glyphs but also
dropped the "do not break" property of the sequence — users relying
heavily on `&nbsp;` could see a line break exactly where they had
written one to prevent it.

Pipeline is now:

* HTML entities `&#160;` and `&nbsp;` decode to the actual
  character **U+00A0** (non-breaking space). A bare U+00A0 that
  was already in the input is kept as-is.
* `wrap_text` splits on ASCII space only (regex `/\s/` does not
  match U+00A0 in Crystal), so a word pair joined by U+00A0 stays
  on the same line.
* Just before each `page.text` call (`draw_text_run` in the
  converter and `InlineRenderer.render_line`), U+00A0 is replaced
  by an ASCII space in the drawn string — the PDF is visually
  clean regardless of whether the active font has a drawable
  NBSP glyph.

Net effect: the visual result is identical to v2.3.24.5 (no tofu)
but line breaks now honour the author's non-breaking spaces.

== v2.3.24.5 — 2026-04-23

Broader flag rendering plus a handful of white-space glyph fixes.

* **Flags in paragraphs, admonitions and lists** too — not just in
  tables. `draw_text_run` is now called from `convert_paragraph`
  (via `InlineRenderer.render_line`), `render_admonition`,

  `<br>` is left for a future pass.

  AsciiDoctor preserves line breaks from the source inside
  paragraphs. The inline renderer and `strip_inline_markup` now
  collapse any run of whitespace into a single space before the
  text is drawn.
* **Fix non-breaking-space tofu**: `&#160;`, `&nbsp;` and bare
  U+00A0 are now normalised to an ordinary space (the non-break
  property is lost, which is an acceptable trade-off given Type1
  standard fonts don't always expose a drawable NBSP glyph).
* **Dependency bump**: `pdf` → uses v0.3.3 via `~> 0.3`,
  which adds a document-scoped cache of `SVG::Parser` instances so
  repeated flags on the same document are parsed only once.

== v2.3.24.4 — 2026-04-23

Real country flags in table cells, via a new SVG rendering pipeline.

* **New dependency** `flags` (~> 0.1) — 271 ISO 3166-1 alpha-2
  SVG flags from lipis/flag-icons embedded at compile time.
* **Inline flag rendering in table cells**: pairs of Unicode regional
  indicator characters (e.g. `🇫🇷`, `🇩🇪`) are detected in cell text
  and drawn as actual colour SVG glyphs on top of the text layer, at
  the baseline of the surrounding text. Previously those codepoints
  rendered as tofu boxes (DejaVu Sans has no glyph for them) and
  threw off the cell width calculation.
* **Layout**: `text_width` and `wrap_text` now charge each flag as a
  fixed width derived from the font size, so columns reserve the
  correct amount of space instead of counting the `.notdef` width
  from the text font.
* **Dependency bump**: `pdf` → `~> 0.3` (uses the path-parser
  loop fix and the closed-shape fill fix shipped in pdf
  v0.3.1 and v0.3.2).
* New helper module `AsciidoctorPDF::InlineFlags` with `segments`,
  `flag_width` and `flag_height`.

== v2.3.24.3 — 2026-04-23

Layout and typography fixes observed on real-world documents.

* **Admonitions** (NOTE, TIP, IMPORTANT, WARNING, CAUTION): the label
  now has a proper gap before the text. Previously the label fit in a
  fixed 60 pt slot regardless of its rendered width, which made long
  labels like `IMPORTANT` visually collide with the first word of
  the message.
* **Section titles**: long titles are now wrapped across multiple
  lines instead of being rendered past the right margin (and
  truncated). Uses the existing `wrap_text` helper with the heading
  font.
* **Table cells**: words that do not fit in their column (typical
  for country names in narrow proportional columns, e.g. `Allemagne`
  or `Pays-Bas`) are now broken into sub-chunks. Break priority:
  internal hyphens (`Pays-` + `Bas`), camelCase boundaries, then a
  per-character fallback. No visual overflow into the neighbouring
  column any more.
* **Default body font size**: lowered from 10.5 pt to 10 pt. Mostly
  cosmetic — makes dense tables fit better on A4 without changing
  the heading hierarchy.
