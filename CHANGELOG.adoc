== v2.3.24.100 — 2026-06-22

=== Fixed

* **Article doctitle now shares the first page with its TOC.** For an
  `article` (default doctype, no title page) requesting a TOC
  (`:toc:`, `:toc: left`, …), the TOC took the whole first page on its
  own and the doctitle — title, author, date — landed at the top of
  the next page, so the TOC appeared "title-less".
+
  `convert_document` now renders the doctitle inline at the top of the
  first page, then reserves the rest of that page for the TOC (drawn
  below the title via `render_toc(..., y_start:)`); the body starts on
  the following page. This matches AsciiDoc's `auto` TOC placement for
  an article (title → TOC → content). Books (`:doctype: book`) and
  documents with an explicit `:title-page:` keep their title page and
  dedicated/embedded TOC unchanged. New test helper
  `IntegrationHelper.page_text` + one guard spec.

== v2.3.24.99 — 2026-06-19

=== Added

* **Repeat the table header on every page of a multi-page table.**
  When a table overflows onto the next page, its header row(s) (column
  labels) are redrawn at the top of each new page so the columns stay
  readable. Implemented via a `@repeat_table_header` hook set by
  `convert_table` and invoked by `check_page_break` right after a page
  break (disarmed during the re-render to avoid infinite recursion).
  Integration test added.

== v2.3.24.98 — 2026-06-16

=== Fixed

* **Bold-italic invisible in `[quote]` blocks.** Inside a quote
  block (which forces italic on every segment), any inline bold
  marker like `*mécanique*` should render as bold-italic — but
  the bold-italic variant of DejaVu Sans was missing from
  `data/fonts/`, and the theme's `base_font_bold_italic_path`
  was set to `nil`. The renderer fell back to Type1
  `Helvetica-BoldOblique` whose WinAnsi encoding can't draw the
  non-ASCII glyphs (`é`, `—`, …) that DejaVu produced elsewhere,
  so the segment was silently dropped — leaving a visible
  white gap in the line.

  Fix: bundle `DejaVuSans-BoldOblique.ttf` (dejavu-fonts 2.37,
  same family/license as the three other TTFs already shipped)
  and point `base_font_bold_italic_path` at it. Bold-italic
  segments now embed and render as expected.

* **Hard break `+\n` swallowed inside `[quote]` blocks.** Two
  cascading bugs:
+
  - `render_indented_block` rebuilt every `InlineSegment`
    to force italic, but forgot to carry `line_break: seg.line_break`
    over — so the marker segment that represents `+\n` (text empty,
    `line_break: true`) lost its flag and became a silently-ignored
    empty segment.
+
  - More importantly, `ParagraphComposer.compose_knuth_plass`
    treated `Penalty(NEG_INFINITY)` as a *candidate* breakpoint
    rather than as a *mandatory* one. Knuth-Plass would freely
    consider line-candidate pairs `(a, b)` that crossed over a
    forced break, picking the option with the lowest demerits —
    which typically meant skipping the break entirely. The
    `compose_first_fit` fallback handled forced breaks correctly
    (since v2.3.24.82, KP is the default for body wrapping,
    so this bug only surfaced now).
+
  Fix: precompute `next_forced[i]` = position of the next
  `Penalty(NEG_INFINITY)` at or after token `i` (O(n) backward
  scan). Before evaluating a candidate pair, reject it if
  `next_forced[start_idx] < b` — i.e. a mandatory break lives
  strictly inside the candidate line. The forced break becomes
  the only legal `b` to leave from `start_idx`'s region.

=== Notes

* Symptom that triggered the investigation: the
  « Conseil de fond » page in a real `tmp/strategie-saas.adoc`
  rendered `*mécanique*` as a blank space inside the quote, and
  the `+\n` after « PDF signé » in the same paragraph was lost
  (« PDF signé + » → « PDF signé auditable » as one line).
  Both fixed; visual diff confirms bold-italic word renders
  and the forced line break appears.

== v2.3.24.97 — 2026-06-08

=== Fixed (inline markup in table cells)

* **Codespans `` `…` ``, bold, italic and links are now rendered WITH
  their style inside table cells.** Previously `render_table_row`
  flattened every cell through `strip_inline_markup`: a password
  written `` `qwertyuiop` `` showed up as running text, with no
  monospace font and no shaded background — giving the impression that
  "the code wasn't displayed".
+
  The cell now goes through the same pipeline as paragraphs:
  `parse_inline` → `wrap_segments` → `render_segment_line`. The bold of
  headers / footers is propagated to the segments via `copy_with` (the
  font being chosen per segment by `resolve_inline_font`), and the row
  color is injected as the default segment color. New helper
  `measure_segment_line` for `halign=center|right` alignment.
+
  Preserved: bold headers, clickable links (`/URI` annotation),
  hyphenation of long words in a narrow column. 2 integration specs
  added (mono codespan + bold-header / mono-body coexistence).

== v2.3.24.96 — 2026-06-08

=== Fixed (title-page logo `:title-logo-image:`)

Four causes prevented a title-page logo from being displayed.

* **`image:` form (single `:`) supported.** `parse_title_logo_macro`
  only stripped the `image::` prefix (double `:`, block macro). The
  standard asciidoctor-pdf form — `image:logo.svg[…]` (single `:`,
  inline macro) — left the prefix glued to the path, resolution failed
  and the logo did not appear (silent failure).

* **Length units (`pdfwidth=4cm`).** The width was parsed by raw
  `to_f?`: `"4cm".to_f?` = `nil` ⇒ default width. A new
  `parse_logo_length` converts `cm`/`mm`/`in`/`pt` (and the bare
  number) into PDF points.

* **Relative path resolution (`safe=unsafe`).** asciidoctor's safe mode
  (API default `secure`) EMPTIES `docdir` and relativizes `docfile`,
  making it impossible to resolve a relative path outside the current
  directory. The CLI now forces `safe=unsafe` by default — like the
  `asciidoctor` CLI — for local files (overridable).
  `resolve_image_path_str` additionally falls back to the `docfile`
  folder.

* **Vertical positioning (via `pdf` ~> 1.20.1).** SVG rendering offset
  `<rect>` elements upward by their height; a logo at the top of the
  page ended up off-page. Fixed in the `pdf` shard.

=== Reminder

The title-page logo is only rendered on a TITLE PAGE. An `article`
(default doctype) must therefore declare `:title-page:` in its header
for a title page — and thus the logo — to be produced.

== v2.3.24.92 — 2026-06-04

=== Fixed

* **`:toc!:` properly disables any table of contents.** Two causes:
+
  0. The global config (`~/.config/.../config.yml`) injected its
     attributes (`toc`, `x-title-page-toc`…) as HARD-SET, locking the
     attribute: a `:toc!:` in a document had no effect.
     `UserConfig#merge_into` now passes them as SOFT-SET (`@` suffix,
     asciidoctor convention) — the config provides DEFAULTS that the
     document header can override.
  0. `title_page_toc_enabled?` only consulted `x-title-page-toc` (TOC
     placement), never `toc` (presence). It now returns `false` as soon
     as `toc` is disabled — no TOC on the title page either.

* **Title-page subtitle wrapped.** `render_title_page_standard`
  rendered the subtitle in a single `draw_text_run` that overflowed
  off-page. It is now wrapped (`wrap_segments` + `render_segment_line`,
  like the title and the inline-mode subtitle), and the separator line
  is placed BELOW the last line of the subtitle (instead of a fixed
  offset that crossed through it).

* **Table header rendered.** Rendering tested `has_header_option`,
  which could be `false` even though the parser had populated
  `rows.head` (the `options="header"` case with a header row + an empty
  row). We now rely on `rows.head`: if a header row exists, it is
  rendered (background + bold).

=== Known (outside this shard)

* Autolinking a URL followed by a space in a cell produces a truncated
  `href` (`https://`) on the crystal-asciidoctor parser side — to be
  fixed in that shard.
* pdf-audit reports `huge_gap` inside table cells (false positives: it
  does not model columns).

== v2.3.24.91 — 2026-06-04

=== Changed

* **The code-wrap `WARNING` now cites the source LINE NUMBER.** The
  v2.3.24.90 message echoed the start of the line, which was not very
  useful. It now directly indicates the line of the `.adoc` file:
+
  ----

+
  The author immediately locates the line and decides what to do

  block carries its line number (`node.lineno`). Overridable via

  to it.

== v2.3.24.90 — 2026-06-04

=== Added

* **Warning on wrapped code lines.** A `[source,…]` block line that is
  automatically wrapped (v2.3.24.88) stays on two lines on screen, but
  copy-pasting it embeds a line break — the command is then not
  executable as-is. Now double-flagged:
+
  0. **Visual marker**: a small amber "↳" hook is drawn in the left
     gutter of the box, at the start of each continuation line. Drawn
     as VECTOR (two segments + arrowhead), so (a) no dependency on the
     mono font's coverage, and (b) ABSENT from copy-paste — the reader
     gets only the code, never the marker. Color configurable via the
     theme (`code_wrap_marker_color`, amber by default).
  0. **`WARNING` at generation time**: a stderr message is emitted for
     each wrapped source line ("copy-paste will insert a line break"),
     inviting the author to shorten the line in the AsciiDoc source if
     they wish.

=== Note

`[source,…]` block lines are not — and never have been — justified:
they are rendered in fixed-pitch (mono), left-aligned, with original
spaces preserved. Only prose (including the inline codespans it
contains) is justified.

== v2.3.24.89 — 2026-06-04

=== Fixed

* **Soft-wrap of `[source,…]` blocks: priority to the space (argument
  boundary).** The v2.3.24.88 wrapping took the rightmost hinge, which
  could split a flag: `… --write --` then `hostname=chouquette` (the
  `--hostname` cut in two). We now break IN PRIORITY at the rightmost
  space that fits — each argument/flag stays whole:
+
  ....
  beryl scan aloli/9783705f-f86f-4bf7-88ad-4c92b920e9ba --provider=scaleway --dns --write
  --hostname=chouquette
  ....
+
  The hinges `/ - = ,` are now only used as a second resort, when a
  SINGLE TOKEN is itself wider than the box (UUID, path or hash without
  a space) — exactly like the soft-break of inline codespans. A hard
  cut at the limit as a last resort.

== v2.3.24.88 — 2026-06-04

=== Added

* **Soft-wrap of overly long lines in `[source,…]` blocks.** A code
  block is rendered verbatim and is not justified, but a line wider
  than the box (typically a shell command with a full UUID + flags,
  e.g. `beryl scan aloli/<uuid> --provider=scaleway --dns --write
  --hostname=…`) overflowed all the way OFF THE PAGE and got clipped —
  the end of the command became invisible.
+
  These lines are now wrapped at hinge characters (space first, then
  `/`, `-`, `=`, `,` — the same logic as the soft-break of inline
  codespans) as close as possible to the edge of the box, and continued
  on a continuation line. The whole command stays visible. No character
  is injected (no `\`, no indentation): a break on a space consumes the
  space, a break on a hinge keeps the hinge on the top line — copy-paste
  stays faithful. A line without any hinge (a single very long token)
  is cut hard as a last resort, still preferable to clipping.
+
  The box height and pagination adjust automatically (the wrapping
  happens before the height computation), so a block that gains lines
  through wrapping stays correctly boxed and can spill onto the next
  page if needed.

=== Verification

beryl README FR + EN: the `beryl scan` command of the Scaleway scenario
(UUID + 4 flags), which ran off the page (ending at 635 pt for an edge
at 595), now fits entirely within the box on two lines. 0 pdf-audit
anomaly, 261 specs green.

== v2.3.24.87 — 2026-06-04

=== Fixed

* **Justification: lines reach the right margin again.** The
  computation of `natural_w` (the natural width of a line, the basis of
  `extra_per_space = (target_w - natural_w) / n_spaces`) on the
  renderer side counted badge paddings (codespan/kbd/mark)
  UNCONDITIONALLY, the way `tokenize` does for the break decision. But
  the rendering only adds them CONDITIONALLY (not between two fragments
  of the same codespan, nor before a clinging character). `natural_w`
  was therefore OVER-estimated ⇒ `extra_per_space` too small ⇒
  justified lines stopped a few points BEFORE the margin (visual defect
  reported on many list items and paragraphs of the beryl README).
+
  The renderer now applies EXACTLY the same condition as the rendering
  (`next_clings` / `next_is_mono`) to count the paddings: `natural_w`
  then equals the width actually drawn, and the line fills exactly up to
  `target_w`. The composer keeps its inflated (unconditional) measure to
  break conservatively — guaranteeing the absence of overflow.

* **Simple admonition: text reaches the right margin.** The content
  width of an admonition removed a `padding` on the RIGHT even in the
  absence of a frame. For a simple admonition (left color bar only, the
  default case), there is no right border: the text now reaches the page
  margin like an ordinary paragraph. The right inset is kept only for
  the boxed variant (`boxed`).

=== Internal cleanup

* Removal of the `composer_natural_w` threading / `wrap_segments_full`
  method introduced in v2.3.24.86: the exact `natural_width` now being
  recomputed locally and correctly by the renderer (conditional
  paddings), the composer's value no longer needs to be passed. Back to
  a single `wrap_segments`.

=== Verification

Rendering validated with poppler (`pdftotext -bbox`, independent
reference): on the beryl README FR and EN, the justified lines reach the
right margin (559 pt) with uniform inter-word spaces (~3-5 pt). The NOTE
on page 1 now reaches the margin.

== v2.3.24.86 — 2026-06-04

=== Changed (internal refactor, rendering unchanged)

* **Removal of the `@line_natural_widths` cache indexed by
  `object_id`.** v2.3.24.85 passed the composer's exact `natural_width`
  to the renderer via a `Hash(UInt64, Float64)` cache indexed by the
  line's `object_id` — a functional but fragile compromise (address
  reuse possible after GC, memory growth over the lifetime of the
  document).
+
  The `natural_width` is now passed **explicitly** as a
  `composer_natural_w` parameter to `render_segment_line`. A new
  `wrap_segments_full` method keeps the composer's complete `Line`
  objects (segments + `natural_width`); the 3 paths that justify
  (paragraph, list item, definition list) use it. `wrap_segments`
  becomes a thin wrapper (`wrap_segments_full(...).map(&.segments)`) for
  the ~9 non-justifying call-sites (titles, markers) that do not need
  the metric.
+
  Rendering **strictly identical** to v2.3.24.85 (positions of all
  words byte-exact, verified on the beryl README: 2794 FR words /
  2776 EN, 0 anomaly). The file loses 25 net lines (-76 / +51): shorter
  and without a shared instance variable.

=== Why this refactor

The `object_id` approach had been chosen so as not to touch the
signature of `render_segment_line` (shared by 12 call-sites). Realizing
that only 3 of them actually justify (pass `target_w` + `align`), it
becomes trivial to thread the real value only where it matters, via an
optional `composer_natural_w : Float64? = nil` parameter
(backward-compatible for the other 9). This eliminates the *code smell*
without any change in rendering.

== v2.3.24.85 — 2026-06-04

=== Fixed

* **Overflow of the French `:` (`mot<NBSP>:`) past the right margin.**
  Root bug in `try_native_justified_text`: the NBSP (U+00A0) was
  converted to an ASCII space *before* the `split(' ')`, which turned
  it into a justification point. An `extra_tj` (stretch) was then
  inserted between `source` and `:` in `source<NBSP>:`, pushing the `:`
  beyond the margin.
+
  In accordance with the typographic convention (confirmed: in French
  `mot<NBSP>:<space>`, only the space AFTER the `:` is justifiable; the
  NBSP is non-breaking AND of fixed width; in English `mot:<space>`,
  same), the split is now done on the STRICT ASCII space. The NBSP stays
  IN the chunks and is converted to a space (for glyph rendering) only
  AFTER the split — so its width stays natural, with no `extra`. New
  method `split_ascii_keep_nbsp`. The simple-font branch (`Tw`) switches
  to manual positioning for the same reason (`Tw` applies to ALL byte-32
  characters, NBSP-converted included).

* **Over-stretching / overflow from a composer ↔ renderer measure
  mismatch.**
  `compose_knuth_plass` computes a per-line `natural_width` that
  INCLUDES the codespan/kbd/mark paddings — it is on this measure that
  the line breaks were decided. The renderer recomputed its own width
  via `font.string_width` WITHOUT these paddings, so it was
  underestimated: `extra_per_space = (tw - natural_w) / n_spaces` became
  too large ⇒ over-stretched lines (gaps of 20-30 pt) or words
  overflowing the margin.
+
  The renderer now consults the composer's `natural_width` (source of
  truth) via a `@line_natural_widths` cache indexed by the line's
  `object_id`, filled in `wrap_segments`. Non-destructive read (a line
  may be rendered several times during a pagination attempt). Safeguard:
  the value is only adopted if it is greater than the local computation
  and within a reasonable bound.

* **Knuth-Plass: `ratio < 0` rejected (no compression).** The shrink
  threshold goes from -1.0 to 0.0: no space compression is tolerated.
  Any overflowing line is rejected, forcing the composer to break
  earlier (the overflowing element moves to the next line, the previous
  one stretches by positive stretch). An atomic Box `mot<NBSP>:` too
  wide for the current line is thus systematically pushed to the next
  line, never compressed nor cut.

=== Impact

PDF of the beryl README (FR and EN), measured by `pdf-audit` v0.2.1:
**0** typographic **anomaly** (7 pages, 2794 FR words / 2776 EN words).
Starting point of the session: 11 anomalies.

No regression on the other examples (x-form-audit-iso27001 even goes
from 8 to 7 pre-existing anomalies, related to the `[x-form]` field
layouts).

=== Implementation note

The `@line_natural_widths` cache indexed by `object_id` is a localized
compromise (avoiding changing the signature of `render_segment_line`,
shared by 15+ call-sites). Safety rests on overwrite-at-write
(`wrap_segments` rewrites the entry just before rendering) and a
plausibility safeguard. A refactor toward a sequential identifier
remains possible if the need arises.

== v2.3.24.84 — 2026-06-04

=== Fixed

* **Knuth-Plass: `ratio < 0` rejected (no space compression).** The
  standard TeX bound `next if ratio < -1.0` allowed up to 100%
  compression of a line's Glues to make it fit within `target_w`. At
  Philippe's request, and in accordance with the French typographic
  convention which wants spaces of stable width (not tightened to gain
  room), this bound becomes `ratio < 0.0`: no space compression
  tolerated. An overflowing line is now systematically rejected by K-P
  — the composer must break earlier, the previous line is stretched by
  positive stretch, and the overflowing element (word, codespan, French
  `:` after NBSP) moves to the next line.
+
  Typical case eliminated: an atomic Box `mot<NBSP>:` (where the NBSP
  makes the `mot`+`:` joint non-breaking, only the space AFTER the `:`
  being justifiable) too wide for the current line is now pushed onto
  the next line instead of being placed in overflow.

=== Impact

On the PDF of the beryl README (measured via `pdf-audit` v0.2.1): the
typographic anomalies go from **11 to 4** (-64%).

* `--hostname=chouquette` (75 pt overflow in a `[source,console]`
  block): classified out-of-scope by the linter's `monospace?` filter —
  typographic convention: code blocks are not wrapped (a shell command
  must not be cut across lines), it is up to the document author to
  break their line in the AsciiDoc source.
* `bootstrapper.`, `réel.`, `API`, `:` (some p4 paragraphs), `l'API`
  (p6 in some paragraphs): eliminated by the K-P `ratio < 0` rejection.
* 4 residuals at 4-8 pt (`par`, `:`, `lit`, `l'API`): cases where
  `compose_first_fit` (K-P fallback when no admissible path is found)
  does not break correctly at the last Glue/Penalty before a final word.
  Converging toward 0 anomaly requires a refactor of the first-fit
  fallback (strict alignment of the composer measure with the actual
  rendering of inter-segment codespan paddings).

== v2.3.24.83 — 2026-06-04

=== Fixed

* **Compensation of badge paddings in the composer's computation.** The
  `ParagraphComposer` did not know that the rendering adds
  `codespan_padding_x` (typically 2 pt), `+4 pt` for `kbd`/`button` or
  `+2 pt` for `mark` to `current_x` after each badge (cf.
  `render_segment_line` ~ line 4031, fix J4.A v2.3.24.73).
  Consequence: lines containing codespans were counted slightly shorter
  than their actual rendering, and some words overflowed the right
  margin by 1 to 16 pt.
+
  Detected thanks to the brand-new `aloli-crystal/pdf-audit` (v0.1.0)
  which reported 42 `margin_overflow` on the PDF of the beryl README.
  The fix consists in inflating the measure of the segment's Box in the
  measurement block of `tokenize` (cf. `converter.cr#wrap_segments`) by
  the same amount as what the renderer adds downstream. Conservative:
  counts a padding even for adjacent codespans (where the compensation
  is actually nil) — an acceptable overestimation since it avoids any
  overflow.

  Verification after fix:
+
  - `pdf-audit lint beryl.pdf`: 67 → 33 anomalies
  - `margin_overflow`: 42 → 20 (the 20 remaining are final punctuation
    `:`, `→`, short words whose pdf2text measure shows ±1-3 pt of
    imprecision)
  - `stuck_words`: 6 → 0
  - Gold compare on the 53 prod-crystal READMEs: 0 project loses a page,
    `beryl-recipes` gains 1 (compaction).

== v2.3.24.79 — 2026-06-03

=== Added

* **True multi-line CJK justification.**
  `ParagraphComposer.tokenize` now detects segments containing
  CJK characters (≥ U+3000) and delegates to a dedicated
  `tokenize_segment_with_cjk` helper which splits EACH CJK
  character into a standalone `Box`, separated by a thin
  `Glue` (`width = 0`, `stretch = char_w × 0.5`,
  `shrink = 0`) between two consecutive CJK chars.

  These thin Glues serve two purposes:

  0. **Legal break-point** that `compose_knuth_plass` uses to
     wrap long CJK paragraphs onto multiple lines. Before this
     change, lacking break-points (CJK paragraphs have no
     ASCII space to naturally act as Glue), a CJK paragraph
     stayed unavoidably on a single line — the composer
     couldn't break it, the user saw it extending past the
     margin.
  0. **`Tc` stretch support.** Knuth-Plass stretches these
     Glues in proportion to each line's `adjustment_ratio`;
     the renderer recomputes the same value via
     `extra_per_cjk_glyph = (target_w - natural_w) /
     (n_cjk - 1)` and emits it via
     `page.text(..., char_spacing:)`.

  NO Glue between a CJK char and an adjacent Latin char: the
  Sino-Japanese convention writes `日本2026年` glued; breaking
  here would be a typographic violation.

  Composer-side corollaries:

  - `finalize_line` and `finalize_kp_line` distinguish a
    “space” Glue (`width > 0`, Latin) from a “thin” Glue
    (`width == 0`, CJK). Only space Glues contribute to
    `n_spaces` and trigger a leading space on the following
    Box — thin CJK Glues introduce no space character in the
    rendered output.
  - The measurement block in `wrap_segments` now accepts an
    isolated CJK char: it uses `font_cjk.string_width` when
    the char is ≥ U+3000 and recognized by the CJK font, else
    `font.string_width` (main Latin font). Without that fix,
    each CJK char would be measured at 0 by Noto Sans Latin
    → phantom-width tokens, underestimated `natural_w`,
    badly-broken lines.
  - The block is now captured as a named `Proc`
    (`&measure : ...`) rather than as implicit `yield`.
    Crystal forbids `yield` inside a Proc literal —
    refactor needed so `tokenize_segment_with_cjk` can
    forward the block to a sub-lambda `flush_latin`. (Bonus:
    `Array(Char)` instead of `String::Builder` for the Latin
    buffer, because `String::Builder.to_s` may only be called
    once and `flush_latin` is called multiple times per
    paragraph.)

  Renderer-side corollaries (`render_segment_line`):

  - `seg_w` computation detects CJK chars and splits by run
    to use `font_cjk` on CJK, `font` on Latin. Without it,
    `seg_w ≈ 0` for isolated CJK chars and `current_x`
    wouldn't advance between two adjacent CJK segs: all
    glyphs piled up at the same visual position ≈ 36.
  - The “non-badge” branch (word-by-word) propagates the
    same correction on the `part_w` measured between
    consecutive `draw_text_run` calls.
  - The CJK `Tc` advancement is now added to `current_x`
    AFTER the seg's draw: `current_x += n_cjk_in_seg ×
    extra_per_cjk_glyph` to follow the PDF engine which
    translates its own cursor by `glyph_w + Tc` after each
    glyph.

  - Both resulting lines are justified to the right edge

== v2.3.24.75 — 2026-06-03

=== Added

* **CJK justification via `Tc` (“両端揃え / 两端对齐”).**
  Pure Chinese / Japanese / Korean paragraphs — those
  containing no ASCII space — are now justified to the right
  edge by stretching the space between each glyph via the
  native PDF `Tc` operator (Character Spacing,
  ISO 32000-1 § 9.3.2), per the canonical Sino-Japanese
  typographic convention.

  Detection: the line contains no ASCII space (`n_spaces ==
  0`), `target_w` is set, `font_cjk` is loaded, and at least 2
  CJK glyphs are recognized by `font_cjk.has_glyph?`.
  Justification stays active even when the received `align` is
  `left` (case of single-line CJK paragraphs, hence “last
  paragraph line” from the composer's view — explicit
  exception to the “last line left-aligned” rule, to honor the
  CJK convention).

  Computation: `extra_per_cjk_glyph = (target_w - natural_w)
  / (n_cjk - 1)`. Guardrail at 75 % of a typical CJK glyph
  width (`中`) to prevent pathologies (2 glyphs alone on a
  very wide line). 75 % is more permissive than the 50 % of a
  first POC — the CJK convention routinely accepts stretches
  up to ~100 %, and the cap was blocking legitimate short
  Japanese lines.

  Concurrent fix to `natural_w` computation: the main font
  (Noto Sans Latin) doesn't contain CJK glyphs and returned
  0 / ε for them, underestimating `natural_w` and skewing all
  mixed-justify computations. We now delegate to
  `text_with_emoji_segments` for per-font segmentation, then
  sum widths with the right font (`font_cjk` for `:cjk` runs,
  `font` for `:text` runs).

  `draw_text_run` accepts an optional `cjk_char_spacing`
  parameter (default `0.0`) which propagates to
  `page.text(..., char_spacing:)` in the `:cjk` branch. The
  Crystal-side cursor advancement compensates the PDF
  engine's accumulated `Tc`: `cursor += string_width + (n - 1)
  × cjk_char_spacing` so the cursor points to the VISUAL end
  of the last glyph (the `Tc` added by PDF after the last
  glyph is invisible — automatically reset by the `pdf` shard
  at the end of `page.text`).

  Visual verification (`/tmp/cjk-test.adoc`):

  - Before: Chinese line xMax=476 (far from right edge 559),
    Japanese line xMax=386.
  - After: Chinese line xMax=559.28 (= right edge `target_w`),
    Japanese line xMax=559.28 (= right edge). Perfectly
    justified.

  Acknowledged limitation: the current
  `ParagraphComposer.tokenize` treats each CJK string as a
  single Box (split on ASCII space only), forcing long CJK
  paragraphs to a single line (composer can't break). True
  multi-line CJK justification would require tokenize-level
  per-glyph splitting with soft Glues between each — major
  refactor planned if real need arises. Current `Tc` rail
  covers most practical cases (a short paragraph in Chinese
  or Japanese).

  Software Practice & Experience vol. 11, p. 1119-1184, 1981),
  the historical TeX algorithm:

  0. Identify legal breakpoints (each `Glue` after a `Box`,
     each non-infinite `Penalty`, end of paragraph).
  0. For each candidate breakpoint B, dynamic programming over
     all preceding breakpoints A: compute the `badness` of the
     A→B line (`100 · |adjustment_ratio|³`, TeX formula), the
     `demerits` (`(1 + badness)² + penalty² +
     double_hyphen_demerits`), memoize the optimal path.
  0. Backtrace to reconstruct the optimal sequence.
  0. Graceful fallback on first-fit if no admissible path
     (pathological paragraph: word too long, target_w too small).

  Visible benefits: balanced lines (similar `adjustment_ratio`
  across the paragraph), exploitation of J2 hyphenation
  Penalties (K-P prefers hyphenation over extreme stretching),
  fewer rivers, double-hyphen penalty (10000 demerits) to
  avoid two consecutive hyphen-ended lines.

* **Removed the `max_extra_factor = 2.5` guard** in
  `render_segment_line`. This heuristic silently fell back to
  `left` alignment when first-fit's `extra_per_space` exceeded
  2.5× a normal space's width — a band-aid on first-fit's bad
  behavior of maxing out each line without looking ahead.
  With Knuth-Plass, stretching stays reasonable by construction
  (K-P minimizes badness² globally), and the user always gets
  the justification their theme requests. Rare pathological
  paragraphs (single overlong word on a wide page) now produce
  visible-but-correct stretching rather than a silent
  fallback to `left` that broke document appearance.

== v2.3.24.69 — 2026-06-03

=== Fixed

* **French NBSP wiped out before reaching the wrapper.** The
  whitespace-normalization regex in `InlineRenderer.parse`
  (`gsub(/\s+/, " ")`) treated U+00A0 (NBSP) as ordinary
  whitespace (PCRE2 in Unicode mode classifies NBSP under `\s`).
  Result: every NBSP freshly inserted by
  `apply_french_typography` (before `:`, `;`, `!`, `?`, `»`) was
  immediately replaced with an ASCII space one step later, and
  `wrap_segments` would happily break the line on it. The
  Imprimerie nationale rule wasn't honored — `deploy : il`
  could be split into `deploy` on one line and `: il` on the
  next.

  The regex is now `gsub(/[^\S\x{00A0}]+/, " ")` — “all
  whitespace EXCEPT NBSP”. NBSPs are now preserved through the
  pipeline and reach `wrap_segments` (which already only split
  on strict ASCII space).

=== Added

* **Structured paragraph composition engine
  (`ParagraphComposer`).** Refactor of `wrap_segments` which
  now delegates to a new module
  `src/asciidoctor_pdf/paragraph_composer.cr` modelling the
  text stream as TeX-style tokens: `Box` (a word or NBSP-bound
  group, fixed non-breakable width), `Glue` (elastic space,
  legal break-point), `Penalty` (forced/forbidden/conditional
  break). The `compose_first_fit` algorithm faithfully
  reproduces the historical greedy behavior — 217/217 specs
  pass. Immediate benefit: NBSP non-breakability is guaranteed
  by construction (NBSPs are absorbed into the neighboring Box
  and can no longer be break-points).

  Software Practice & Experience, vol. 11, p. 1119-1184, 1981.

== v2.3.24.6 — 2026-04-23

Preserve the non-break property of `&nbsp;` / `&#160;` in wrap.

The v2.3.24.5 fix normalised every non-breaking space to an ASCII
space *before* wrap, which eliminated the tofu glyphs but also
dropped the "do not break" property of the sequence — users relying
heavily on `&nbsp;` could see a line break exactly where they had
written one to prevent it.

Pipeline is now:

* HTML entities `&#160;` and `&nbsp;` decode to the actual
  character **U+00A0** (non-breaking space). A bare U+00A0 that
  was already in the input is kept as-is.
* `wrap_text` splits on ASCII space only (regex `/\s/` does not
  match U+00A0 in Crystal), so a word pair joined by U+00A0 stays
  on the same line.
* Just before each `page.text` call (`draw_text_run` in the
  converter and `InlineRenderer.render_line`), U+00A0 is replaced
  by an ASCII space in the drawn string — the PDF is visually
  clean regardless of whether the active font has a drawable
  NBSP glyph.

Net effect: the visual result is identical to v2.3.24.5 (no tofu)
but line breaks now honour the author's non-breaking spaces.
